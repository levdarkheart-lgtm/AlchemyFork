### P3 remaining inherited ownership-state defect: temporary boosts leave NO_DELETE behind

`LLViewerTexture::addBoostHold/boostThisFrame` reaches `updateBoost` (`llviewertexture.cpp:821-840`). A temporary PREVIEW or HUD effective boost writes `NO_DELETE` at lines 858-864. Releasing the last holder (`removeBoostHold`, lines 827-834) or lapsing the frame boost (843-848) recalculates the effective numeric boost correctly but never restores the previous texture state when the effective level returns to NONE. `ALTextureBoost::release` does only the counted release plus reference drop (`altextureboost.cpp:77-83`), and ordinary `LLGLTexture::setActive` refuses to change NO_DELETE (`llgltexture.cpp:121-126`). Therefore a texture initially ACTIVE, temporarily held by a preview/HUD and then released, retains the observable NO_DELETE state. The scoped model tests do not instantiate the production LLViewerTexture owner and cannot detect this.

This is an inherited setter/state behavior retained by the port, not a proved new native memory leak or demonstrated performance regression. The current native lazy image flush uses reference count and timeout without checking NO_DELETE (`llviewertexturelist.cpp:1097-1112`), and native downscaling is not gated by this flag. Profile images already have a caller-specific `mWasNoDelete` / `forceActive` workaround (`llprofileimagectrl.cpp:55-65,115`), which further shows this state is not generally owned by the RAII holder. Record it as remaining ownership cleanup; preserve explicit `dontDiscard`, role boosts, and other live holders when fixing it. Do not unconditionally force ACTIVE on every holder release. A meaningful regression should exercise two real LLViewerTexture holders, role boost preservation, final release, and frame lapse through the production owner. No accounting/retirement redesign is required to document this gap.
