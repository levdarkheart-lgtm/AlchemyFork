# Aurora render ownership and GPU-driven work: source audit

Scope: public Aurora Viewer checkout `/private/tmp/aurora-threading-analysis-20261111`, commit `a6340067e020d003f8f8e32e0e8be5bd84ff9e33`. Static source analysis only; no Aurora execution, build, GPU capture, or performance test. References below point to this exact commit. Current Alchemy observations are pinned to `578191f6c66edc3e8f4823e4ffefb07ac29c2778`; no original Alchemy baseline or historical performance results are used here.

## Finding: Aurora has an actual ownership split, not merely a render-thread name

`aurora-render/src/lib.rs:118` exports `main_thread::Renderer`. In the viewer's ordinary frame path, `aurora-viewer/src/app.rs:10421` builds the scene lists, and `:11788–11804` calls `gfx.renderer.render(fp, lists, Some(egui_frame))`. That is the real application's path; the render thread is not a standalone experiment or a test-only renderer.

`main_thread.rs:692–696` calls `Host::new(backend, window, thread_wanted(...))`. `render_thread.rs:286–305` defaults the render thread on, unless `AURORA_RENDER_THREAD` is one of 0/off/false/no. Thread creation failure uses the inline execution host for the same packets. `render_thread.rs:378–410` owns the backend on `aurora-render`, takes each owned job, calls `backend.render(*packet)`, publishes the result, and separately services GPU pacing. Hence there are two CPU stages that can overlap: simulation/UI/list preparation for frame N+1, and resource replay/encoding/submission/present for N.

Sources: [normal application handoff](https://github.com/Aurora-Viewer/Aurora-Viewer/blob/a6340067e020d003f8f8e32e0e8be5bd84ff9e33/crates/aurora-viewer/src/app.rs#L11788-L11804), [default-on host](https://github.com/Aurora-Viewer/Aurora-Viewer/blob/a6340067e020d003f8f8e32e0e8be5bd84ff9e33/crates/aurora-render/src/render_thread.rs#L286-L305), [worker execution](https://github.com/Aurora-Viewer/Aurora-Viewer/blob/a6340067e020d003f8f8e32e0e8be5bd84ff9e33/crates/aurora-render/src/render_thread.rs#L378-L410).

This differs from merely letting the GPU execute frame N while one CPU thread prepares N+1. Alchemy already has asynchronous GPU submission; Aurora additionally moves the CPU renderer behind an owned handoff. The ideal throughput benefit is moving CPU work from a serial sum toward the longest stage, but that is a model, not a measured speedup for Alchemy. If Alchemy is limited by GPU shaders/pixels, moving encoding to another CPU core cannot shorten that GPU work.

## Packet design: a compact frame view and ordered deltas, not a full world copy

`packet.rs:107–138` defines `FramePacket`. It owns the frame index, write journal, streamed uploads, `SceneGpu`, `FrameParams`, copied CPU `DrawLists`, egui shapes/deltas, surface dimensions/vsync, render settings, hover/click/drawn-face requests, capture request, histogram request, motion-history cut and input timestamp.

The backend never traverses the mutable scene stores. Main-thread ownership includes record/face/object mirrors, geometry allocators, texture slots/pages, joint palettes/skin bindings and upload staging. Backend ownership includes surface, pipelines, targets, per-frame uniforms, egui GPU state, compute culling/bins, occlusion and readbacks (`main_thread.rs:3–34`). The boundary is explicitly about *what* to draw versus *how* to draw.

`SceneGpu` (`packet.rs:69–98`) contains reference-counted GPU buffer/bind-group handles plus table sizes and generation keys. `main_thread.rs:151–177` clones those handles at handoff; growth/replacement in the next main-thread frame therefore does not destroy the resources the previous packet names. This is handle retention rather than duplicating all GPU storage each frame.

At `main_thread.rs:1391–1396`, dirty record/face/object/bounds mirrors flush into this frame's journal and uploads are detached. At `:1419–1455`, it swaps the journal into a spare packet allocation, copies CPU draw lists into reusable vectors, captures current GPU handles and takes request lists. At `:1467` it sends the packet by ownership. On the way back, `FrameResult` has statistics, asynchronous results, and `Spent { writes, lists }`; `:1229–1263` applies the returned results and recycles these allocations (up to two spare packets). This does still copy CPU list elements and dirty bytes; it is not a zero-copy or no-allocation architecture, but it does not clone the entire simulation world.

Sources: [packet fields and resource handles](https://github.com/Aurora-Viewer/Aurora-Viewer/blob/a6340067e020d003f8f8e32e0e8be5bd84ff9e33/crates/aurora-render/src/packet.rs#L69-L160), [handle snapshot](https://github.com/Aurora-Viewer/Aurora-Viewer/blob/a6340067e020d003f8f8e32e0e8be5bd84ff9e33/crates/aurora-render/src/main_thread.rs#L151-L177), [packet construction](https://github.com/Aurora-Viewer/Aurora-Viewer/blob/a6340067e020d003f8f8e32e0e8be5bd84ff9e33/crates/aurora-render/src/main_thread.rs#L1391-L1455), [reuse](https://github.com/Aurora-Viewer/Aurora-Viewer/blob/a6340067e020d003f8f8e32e0e8be5bd84ff9e33/crates/aurora-render/src/main_thread.rs#L1228-L1263).

### The correctness step that makes the thread split real

Retaining handles is insufficient when both frames name the same underlying buffer. A main-thread write for N+1 must not become visible to N's encoding/submission. Aurora therefore gives the backend exclusive queue ownership. Main-thread resource creation remains possible through a shared device, but queue writes and submissions become ordered journal operations.

`writes.rs:47–61` records Buffer, Texture and Submit operations. Buffer/texture operations clone their destination handles and copy their bytes into one owned journal byte vector (`:88–125`). Submit entries preserve arena-growth/copy boundaries: preceding writes must take effect before that copy, following writes must not be pulled forward. `renderer.rs:6434–6447` replays this exact journal on the render thread before per-frame uniforms and draws. The journal replay at `writes.rs:171–184` drains operations in their recorded order and reuses/limits byte storage. Persistent GPU records are updated only where dirty; e.g. `arena.rs:712–725` marks changed records and `gpu_cull.rs:625–680` tracks narrower dirty spans rather than always copying whole chunks.

Frame N and N+1 may therefore reuse buffer identities, with their writes and draws correctly ordered on the backend queue. This is temporal ownership of updates, not blanket double buffering. Alchemy's equivalent must account for its *mapped shared Metal buffers*: a CPU memcpy into a reused shared buffer is not made safe by command-queue submission order alone. It must write a distinct protected range/version, stage a blit ordered after earlier readers, or wait for the protected lifetime. This is one of the hard requirements behind moving native encoding off the main thread.

Sources: [ordered write operations](https://github.com/Aurora-Viewer/Aurora-Viewer/blob/a6340067e020d003f8f8e32e0e8be5bd84ff9e33/crates/aurora-render/src/writes.rs#L45-L125), [actual replay](https://github.com/Aurora-Viewer/Aurora-Viewer/blob/a6340067e020d003f8f8e32e0e8be5bd84ff9e33/crates/aurora-render/src/renderer.rs#L6434-L6447).

## Backpressure, completion and latency: three distinct boundaries

The CPU handoff is a rendezvous: at most one outstanding backend job, not an unbounded frame queue. `render_thread.rs:35–60` has one job, busy flag and one result; `:95–126` waits for the existing job before publishing another. However, the application uses a bounded preflight wait (`main_thread.rs:1059–1090`, `:1369–1383`) before building the final packet. The first stalled-frame wait is bounded to 2 seconds, subsequent waits to 50 ms (`:124–130`); writes are retained if the backend stays stuck and egui texture deltas are carried forward. This keeps the window loop able to answer rather than spinning or parking forever.

The worker's `complete(done)` (`render_thread.rs:405`) follows `backend.render()` and precedes `finish_frames_before(frame, GPU_WAIT)` (`:410`). On the normal path, `renderer.rs:9617–9629` submits, records the GPU submission, and installs a submitted-work completion callback. It calls queue presentation at `:9654–9657`, then returns a result at `:9714–9715`. Thus *CPU handoff finished / present was requested* is not *GPU work finished* and not *photons displayed*. Its `input_ms` measures input to present call, not physical display latency.

GPU pacing is separate. `main_thread.rs:1585–1607` waits on completion news for N−1 before N+1 reads input; only the render thread polls/waits on the device. `pacing.rs:142–188` uses smoothed main/render/GPU timings and hysteresis to enable this only while GPU duration covers the CPU stages. Without GPU timestamps, it does not assume the GPU is the limiter. The comments explicitly discuss a throughput penalty when unconditional waits destroy useful overlap; these are source rationale and model, not measurements independently reproduced here.

Capture requests deliberately take a more synchronous path (`main_thread.rs:1478–1496`, bounded 10 s); old blocking pick jobs also exist. Aurora is not entirely nonblocking. On shutdown the host waits up to 3 s, and if a driver holds the worker it leaves the backend and window keep-alive with that stuck thread until process exit (`render_thread.rs:328–359`). This is a deliberate failure tradeoff, not a thread cancellation mechanism or guaranteed driver recovery.

## GPU-driven renderer: changing the amount of CPU work as well as its placement

The ordinary application calls `Scene::build_lists` (`app.rs:10421`). That queries `renderer.gpu_culling()` (`scene/mod.rs:4575`). `main_thread.rs:1023–1024` requires both device support and scene table sizes within device limits. `GpuCull::supported` additionally requires `MULTI_DRAW_INDIRECT_COUNT`, at least eight storage buffers per shader stage and no CPU override (`gpu_cull.rs:951–963`). GPU lists are therefore a real production path but not unconditional on every adapter or scene. No runtime evidence here proves that this path is active on a particular Mac/M1 Max; that must be checked in its runtime feature/log output.

On the enabled path, persistent tables hold one object and one drawable face record, updated only when they change. Each frame compute evaluates object world spheres (including posed/skinned geometry), classifies faces against main/shadow/reflection/probe views, scans group counts and scatters compact indirect arguments. `gpu_cull.rs:1205–1254` actually encodes these passes; `renderer.rs:7578–7590` actually calls it; `:7633–7647` draws GPU bins using `multi_draw_indexed_indirect_count` and GPU-produced counts without a CPU count readback.

The shader implements stable order deliberately. `cull.wgsl:459–497` classifies and counts; `:503–532` prefix-scans workgroup counts; `:570–628` uses per-lane prefix ranks plus group offsets to place commands in record order. This avoids coplanar winner flicker from nondeterministic atomic slot append. Depth-only occlusion lists can use atomics because their ordering is immaterial; occlusion after the first depth/Hi-Z phase is separately encoded. Broadly: stable culling/compaction replaces repeated CPU draw-list construction across views, then a small number of render-bin calls replaces per-face CPU draw encoding.

CPU exceptions remain: terrain/water, alpha blends that need sorting, glow, debug, selection, impostors, particles and HUD work. `packet.rs:14–17` and `Scene::build_lists` show this. GPU culling does not mean the CPU no longer decides avatar representation or builds every special pass. `scene/list_index.rs:12–18,44–50` adds a compact byte index so CPU exceptions scan only relevant object classes rather than large general object records every frame; ordinary default uses that index. These are algorithm/data-layout gains independent of increasing thread count.

Sources: [feature/size gate](https://github.com/Aurora-Viewer/Aurora-Viewer/blob/a6340067e020d003f8f8e32e0e8be5bd84ff9e33/crates/aurora-render/src/gpu_cull.rs#L948-L963), [compute dispatch](https://github.com/Aurora-Viewer/Aurora-Viewer/blob/a6340067e020d003f8f8e32e0e8be5bd84ff9e33/crates/aurora-render/src/gpu_cull.rs#L1203-L1254), [actual count-driven draw](https://github.com/Aurora-Viewer/Aurora-Viewer/blob/a6340067e020d003f8f8e32e0e8be5bd84ff9e33/crates/aurora-render/src/renderer.rs#L7633-L7647), [stable scatter](https://github.com/Aurora-Viewer/Aurora-Viewer/blob/a6340067e020d003f8f8e32e0e8be5bd84ff9e33/crates/aurora-render/src/shaders/cull.wgsl#L558-L628), [compact CPU class index](https://github.com/Aurora-Viewer/Aurora-Viewer/blob/a6340067e020d003f8f8e32e0e8be5bd84ff9e33/crates/aurora-viewer/src/scene/list_index.rs#L1-L50).

For Alchemy: native Metal compute, argument buffers, resource tables and ICBs can implement these concepts. Do not copy Vulkan/wgpu's exact indirect-count API or assume one universal pipeline can replace all Alchemy material/alpha/query semantics. Start with a class with clear order/visibility invariants; keep existing full-feature native rendering while validating the new native optimization. Existing Alchemy shadow ICBs are CPU-prepared, not already this persistent multi-view GPU classifier. GPU-driven work can reduce CPU time more than simply spreading identical repeated work across cores, but adds compute bandwidth, table maintenance, memory limits, resource-residency requirements and debugging complexity.

## Bindless/page layout: actual source and platform-specific motives

`textures.rs:3–15` describes and `:1265–1293,:1403–1418` implements a texture page array plus a slot-location storage table. Draw records use stable u32 slots; the shader resolves page/layer through `tex_loc`, sampling a layer of an array page (`shaders/common.wgsl:252–256`). New streamed textures generally update location entries, rather than rebinding each texture per draw. Pages group compatible size/mip/format textures; they are not one giant arbitrary atlas with new filtering bleed.

Its stated motive includes wgpu-core traversing all bind-group resources per pass/finish/submit. Grouping thousands of textures into fewer page resources reduces that implementation-specific validation/tracking work. Native Metal argument buffers may offer the same material indirection/low CPU-bind advantage, but Alchemy should not copy page packing without measuring its own actual bottleneck, texture residency/mip churn and format constraints. A size/mip/format grouping policy has fragmentation/compaction costs and added indirection; it does not automatically improve cache locality or compression.

Sources: [page rationale and indexing](https://github.com/Aurora-Viewer/Aurora-Viewer/blob/a6340067e020d003f8f8e32e0e8be5bd84ff9e33/crates/aurora-render/src/textures.rs#L1-L26), [shader table](https://github.com/Aurora-Viewer/Aurora-Viewer/blob/a6340067e020d003f8f8e32e0e8be5bd84ff9e33/crates/aurora-render/src/shaders/common.wgsl#L252-L256).

## Helper workers: selective concurrency around known expensive boundaries

The backend constructs two persistent `Helpers` (`renderer.rs:3554`). `Helpers::pair` (`helpers.rs:80–85`) sends independent jobs to them while one job executes on the render thread. The actual frame call `renderer.rs:9592` finishes pre and post encoders on helpers while the scene encoder finishes locally, then appends `[pre, scene, post]` in order and submits them in that order (`:9594,:9617–9621`). This is real production helper use, not just test scaffolding. The comment reports wgpu finish validation/tracking cost; its timings are source-author claims, not reproduced Mac/Alchemy evidence. Native Metal's encoding/finalization costs differ, so copying the exact three-finish layout would be cargo cult. The general lesson is stable long-lived helpers, independent owned jobs, and deterministic dependency submission.

Other actual helpers include `aurora-pipelines` for quality-dependent pipeline compilation (`renderer.rs:5408–5437`), `aurora-pages` creating/destroying streamed texture pages (`textures.rs:212–244`), and `aurora-vram` doing 250 ms budget samples off the frame/UI path (`vram.rs:228–295`). Page allocation can still contend on driver allocator locks with the render thread; moving the call does not erase device-level contention (`textures.rs:189–204`). The write journal also uses pooled staging (`write_staging.rs:1–29`): one staging buffer and merged adjacent GPU copies instead of thousands of tiny queue allocations, capped to three slots/32 MiB each (`:35–42`) with fallback when no safe slot is ready. This is bounded resource design, not maximizing outstanding work.

## Readbacks and interface are part of the architecture, not cleanup work

Aurora's UI handoff owns egui shapes, texture changes and a tessellator state snapshot, rather than asking a render worker to traverse the live UI context (`ui_frame.rs:75–115`). This avoids holding egui's shared context lock throughout tessellation while the next UI frame starts. Alchemy's retained UI needs its own immutable paint-command/font-atlas lease boundary; moving LLView traversal or reading live text widgets from the render thread would not be equivalent.

Picking is ticketed and delayed: `main_thread.rs:1613–1642` requests a depth texel and collects it one to three frames later; the depth readback keeps the camera that generated the depth. `app/click_pick.rs:10–28` and `:523–564` store the original click ray/modifiers and hold dependent button/release/drag inputs in order until the result arrives or times out. A second requested draw-ID pass renders actual GPU-posed geometry to a 2×2 target (`drawn_pick.rs:13–22`), which avoids CPU reskinning but adds request-time vertex work and response latency. Camera-depth picking from the previously presented frame and drawn-face picking from the next requested frame are distinct semantics, explicitly documented. They are not magically a fully atomic input/world snapshot.

A port must also guard stale results after logout/region changes/object deletion or recycled record IDs. The inspected interfaces carry request tickets and frame result indexes; `DrawnFace` itself carries u32 record ID (`drawn_pick.rs:54–65`) and application resolution consults current scene mapping. This audit has not proved every lifecycle/staleness edge or identified an executable bug. Generation-safe object/record identity and invalidation tests are requirements for Alchemy's design, not benefits to assume from ticketing alone.

## macOS correction and comparison limits

At this pinned source, `lib.rs:133–136` selects `wgpu::Backends::METAL` for macOS, Vulkan elsewhere; `main_thread.rs:327–329` actually puts that selection into `InstanceDescriptor`. This is wgpu's Metal backend, not Vulkan through MoltenVK on macOS. `Cargo.toml` has ash only under `not(target_os = "macos")` and objc2-metal on macOS. The README's broad Vulkan wording is less precise than current platform code.

`docs/MACOS.md:12–27` says Metal 3/macOS13 minimum and default world render at logical resolution, upscaled, with a Mac Mid-High profile (no shadows/AO, FXAA, manual probes). Therefore a reported Aurora/Alchemy FPS gap cannot be attributed to threading without matching actual world render resolution and quality features. Source-proven design differences are useful evidence even without comparative FPS; claims of superior M1 Max performance or enabled GPU-count feature paths need runtime verification.

## Recommended native transfer sequence

1. Instrument Alchemy's current native CPU critical path: scene update, cull/sort, native packet construction, palette/constant publication, encoding, queue/drawable/pacing waits. Associate frame/request epochs and separately time GPU spans. This decides which later step can pay off.
2. Define an owned C++ Metal frame packet and explicit view contexts. Replace the current implicit active-camera/capture/global-pass reads at the packet boundary. Preserve existing draw order and all feature flags before threading it.
3. Freeze draw inputs with resource/storage leases and copied palettes, and journal/sequence resource updates. Establish immutable published ranges and GPU-retired reuse. Main thread stays world/UI authority; render owner becomes sole command/queue producer. Add deterministic tests for reallocation, dirty retry, deletion, region change, capture, UI/font atlas and delayed picks.
4. Put native encoding behind a bounded worker handoff, including previous-frame results and separate actual GPU completion. Evaluate throughput and input latency together. Off-thread encoding alone is one meaningful checkpoint, not the final architecture.
5. Convert stable opaque/masked/shadow subsets to persistent tables, native argument buffers/ICBs and compute visibility/compaction where measured. Preserve ordering/dependencies and keep native feature-complete paths while optimization is validated. This removes repeated CPU work rather than redistributing every current draw unchanged.
6. Add helper jobs only for measured independent work; preserve bounded memory, QoS and driver-lock visibility. Rust, wgpu, Vulkan and cross-platform abstraction are not prerequisites for any of the ownership ideas.

Alchemy grounding for steps 2–3: active native hero/probe owner swaps `pipeline.cpp:1684,:1927`; mutable capture vectors `:526`; current-camera draw matrices `:11554`; palette update/raw pointer `:12417–12430`; borrowed scene vectors `:16853–16857`; shared mutable but GPU-completion-safe `ALMetalWorldFrameData` allocator `almetalworld.cpp:1321–1339,:1419–1515`. Those are present-fork native constraints, not criticism of removed GL calls. A GPU-safe allocation lifetime and a CPU-thread-safe producer boundary are different invariants.
